# Feature Specification: Slice 3 — Real Call, Real CRM

**Feature Branch**: `003-real-call-real-crm`

**Created**: 2026-05-25

**Status**: Draft

**Bench Owner**: `py-bench`

**Input**: User description: "Create Feature 003: Slice 3 - Real Call, Real CRM. Prove the full MVP loop with one Dataverse-owned ALF queue item, one real SignalWire outbound call, a live Pipecat real-time audio conversation path, the ALF appointment-setter persona, structured outcome capture, and Dynamics write-back. Add real SignalWire outbound dialing, SignalWire status callbacks, Pipecat real-time audio + configured real-time AI model as the primary conversation path, non-blocking shadow STT with discrepancy logging, hard E.164 / provider-acceptable phone-number validation, and explicit real-call / write-enabled mode. Preserve Slice 1 conceptual contracts and Slice 2 Dataverse mapping/idempotency/retry behavior. No Flutter admin app, no custom UI, no multi-provider telephony, no clinical workflows, no opportunity creation."

## Constitution Alignment *(mandatory)*

- **CRM control plane**: Slice 3 keeps Dynamics 365 / Dataverse as the operational source of truth and the operator surface. The Slice 2 Dataverse queue source, write-back adapter, metadata verification, owner/team mapping, high-confidence value preservation, idempotency-key stamping, bounded retry, and resume behavior are reused unchanged. No parallel campaign UI, custom task queue, transcript console, or CRM replacement is introduced — operator evidence is the Dynamics records plus local audit artifacts and CLI/API output.
- **Thin slice**: Target slice is **Slice 3 — Real Call, Real CRM** from the constitution's binding MVP order. The smallest independently demonstrable outcome is: one eligible Dataverse-owned ALF queue item moves from `ready` to a final disposition after a real outbound SignalWire call, and Dynamics receives the correct Phone Call activity, queue status / attempt / disposition updates, and callback or review Task when warranted. Slice 3 processes exactly one Dataverse queue item per invocation. Batch calling, schedulers, campaign automation loops, distributed job queues, and multi-worker coordination are explicitly out of scope. The narrow Flutter admin/install app exception permitted by the constitution remains an independent `flutterBench` feature stream (Features 004+) and is not part of Feature 003.
- **Boundaries**: The five Slice 1 module boundaries are preserved (Interaction Core / orchestrator, eligibility evaluator, call transport, ALF appointment-setter persona, CRM write-back adapter), with three Slice 3 additions confined behind explicit boundaries:
  - A **SignalWire telephony transport** that satisfies the conceptual call-transport contract proven in Slice 1 (now consuming a `dial_plan` instead of a fixture id), translates SignalWire provider states and webhook callbacks into the normalized openCloser event set, and assigns the real provider call ID.
  - A **Pipecat real-time audio runtime** that bridges call audio to the configured real-time AI model provider and back, drives the ALF persona's conversation turns, emits transcript segments and extraction events, and returns a final structured persona output.
  - A **non-blocking shadow STT lane** that listens to the same caller audio, produces an independent transcript or transcript pointer under the same session and retention policy, and emits discrepancy events for high-value fields.
  SignalWire-specific webhook shapes, Pipecat pipeline configuration, model-provider streaming protocols, and shadow STT provider details MUST NOT leak into the orchestrator, eligibility evaluator, persona, or Dataverse adapter. The persona module continues to own disclosure language, allowed claims, extraction schema, deterministic disposition rules, and escalation reasons; the live model produces conversation turns and extraction events but MUST NOT mutate the deterministic disposition rules or the human-review reason set.
- **Safety and human handoff**: The ALF persona policy from Slices 1 and 2 is preserved without weakening: AI-on-behalf-of-Medx disclosure at the start of every connected call, non-clinical scope, no resident/patient PHI collection, immediate stop on clear opt-out or DNC statements, allowed-claim limits, the same `needs_human_review` reason-code set, and the same deterministic disposition precedence. Slice 3 adds hard real-dial safety gates: an explicit real-call / write-enabled flag is required before any SignalWire dial, end-to-end telephony readiness (credentials, source/destination numbers, callback URLs, persona/runtime mapping, verified Dataverse mapping, callback owner mapping, call-window/DNC/attempt eligibility) MUST pass before dial, hard E.164 / provider-acceptable phone-number validation MUST block before dial, and any blocked or unready result MUST NOT place a provider call, MUST NOT consume an attempt, and MUST NOT create a false Phone Call activity. Callback and review Tasks remain assigned to the configured Dynamics owner/team; DNC outcomes update the Dataverse DNC/opt-out fields and create no follow-up Task.
- **Auditability**: Every processed Dataverse queue item MUST produce a traceable session ID, eligibility decision, real provider call ID when a dial occurred, persona version, runtime/model identity, started/ended timestamps, final disposition, and the CRM correlation identifiers needed to detect and recover from duplicate or failed Dataverse writes. SignalWire status and media callbacks, repeated CLI invocations for the same session, and Dataverse write-back retries after a transient CRM error MUST be idempotent: 100% of duplicates and recovery attempts MUST leave Dynamics with no duplicate Phone Call activities, no duplicate Tasks, no duplicate queue-status transitions, and no duplicate attempt-count increments. Shadow STT discrepancies, when enabled, MUST be recorded as audit/review evidence under the same session and retention policy and MUST NOT block the live call or independently mutate CRM in the MVP. Logs and exported artifacts MUST NOT contain secrets and MUST honor the deployment's transcript-retention policy (full transcript with default-on redaction, summary-only, or pointer-only — operator's choice).

## Definitions

- **Real-call / write-enabled mode**: The CLI run mode in which a SignalWire dial is permitted and Dataverse mutations are performed. Requires an explicit flag or equivalent deliberate action; default invocation MUST NOT place a call or mutate Dynamics. Reuses the Slice 2 write-enabled semantics and extends them so the same flag also unblocks SignalWire dialing.
- **Rehearsal / readiness mode**: A non-mutating CLI mode that verifies Dataverse mapping, SignalWire telephony readiness (credentials presence, source number, destination phone format, callback URL configuration), persona/runtime configuration, eligibility, and the planned dial plan and write-back payloads, producing the planned write-back artifacts and a readiness report — without placing a SignalWire call and without creating or updating any Dataverse record beyond approved dry-run behavior.
- **Telephony readiness check**: The pre-dial verification that all of these are satisfied: SignalWire account/credentials configured and validatable; a configured source caller-ID number authorized for outbound dialing; a destination phone number that passes E.164 / provider-acceptable validation; status and media callback URLs reachable from the SignalWire side and configured; campaign-to-persona mapping resolved; verified Dataverse mapping; callback and review Task owner/team mapping; and local call-window / DNC / attempt eligibility (the existing six Slice 1 eligibility rules promoted to hard pre-dial checks).
- **Telephony readiness failure**: Any telephony readiness check above that fails. A telephony readiness failure MUST exit before placing a SignalWire call, MUST NOT consume an attempt, MUST NOT create a Phone Call activity, MUST NOT advance the Dataverse queue beyond the approved blocked-status write, and MUST be operator-visible in the run report.
- **SignalWire status callback**: A provider-emitted call status webhook (initiated, ringing, answered, in-progress, completed, busy, no-answer, failed, canceled, or carrier-equivalent). Treated as event input to the orchestrator after the transport adapter translates it into the normalized event set.
- **SignalWire media callback**: A provider-emitted media stream connection / hangup / error event tied to the in-progress call, used by the Pipecat runtime to wire audio I/O.
- **Real provider call ID**: The SignalWire-assigned call SID (or carrier-equivalent identifier) for a placed call, recorded on the session and used for correlation with SignalWire status and media callbacks. Replaces the Slice 1/2 "mock provider call ID" concept for Slice 3 while keeping backwards-compatible correlation for fixture-replay debugging and audit inspection of pre-Slice-3 sessions.
- **Normalized call event**: One of the existing `connected` / `no_answer` / `voicemail` / `failed` / `completed` / `callback_requested` event types. Provider intermediate states (initiated / ringing / answered / in-progress, plus carrier failure subtypes such as busy / canceled) MUST be mapped by the SignalWire transport adapter into the call-status-derived subset of this set (`connected` / `no_answer` / `voicemail` / `failed` / `completed`); `callback_requested` remains part of the normalized event vocabulary but is **not** produced from call-status normalization — it is a persona-determined disposition. The orchestrator, eligibility evaluator, persona, and Dataverse adapter MUST continue to speak the normalized event set.
- **Live conversation path**: The primary Slice 3 conversation pipeline — caller audio → SignalWire → Pipecat runtime → configured real-time AI model provider → audio response — that drives the ALF persona's connected-call turns, emits transcript segments, and produces the persona output the orchestrator assembles into the normalized session result.
- **Shadow STT lane**: An optional non-blocking secondary transcript pipeline that listens to the same caller audio, produces an independent transcript or transcript pointer under the same session and retention policy, and emits discrepancy events when high-value fields (opt-out / DNC, wrong number, captured email, callback intent, person reached name/role, interest level, final disposition) diverge from the live conversation path's transcript/log.
- **Shadow STT discrepancy**: A recorded difference between the live conversation path's high-value field value(s) and the shadow STT lane's value(s) for the same session. Stored as audit/review evidence under the session's retention policy; never independently writes a CRM record or overrides the persona's final disposition in the MVP.
- **High-value field**: One of the persona-extracted or persona-classified fields whose audit-quality matters most for downstream review: opt-out / DNC, wrong number, captured email, callback intent / preferred callback window, person reached name and role, interest level, and final disposition.
- **Real-dial phone-number validation**: A pre-dial validation of the destination phone number against E.164 or a provider-acceptable equivalent. A missing, blank, or malformed destination phone number MUST block before the dial, MUST NOT consume an attempt, and MUST NOT create a Phone Call activity. Promotes the Slice 2 data-quality warning to a hard pre-dial block.
- **Attempt consumed (Slice 3)**: A call attempt is consumed exactly once only after eligibility allows the item, run-mode checks pass, real-dial phone-number validation passes, telephony readiness passes, Dataverse metadata verification passes, and the SignalWire dial is successfully placed (real provider call ID assigned). Blocked eligibility, rehearsal/readiness mode, real-call/write-enabled flag absent, telephony readiness failure, real-dial phone-number validation failure, Dataverse-unreachable-at-start, malformed dial-plan / persona-runtime configuration, and provider-rejected dial requests (SignalWire returns 4xx before call placement) MUST NOT increment the attempt count.
- **Live-call abandonment**: A call placed and acknowledged by SignalWire that ends before any normalized terminal event (`no_answer`, `voicemail`, `failed`, `completed`) is received — e.g., orchestrator process termination, runtime crash mid-call, or persistent provider callback delivery failure. Treated as `failed` with a `live_call_abandonment` reason once the configured timeout elapses; MUST NOT leave the queue item in `in_progress` indefinitely; MUST NOT create a false connected-call activity.
- **Allowed claims (Slice 1, restated)** *(per R4-Q11)*: The positive set of statements the ALF appointment-setter persona MAY make — appointment / callback scheduling, general non-clinical description of Medx's ALF outreach purpose, confirming the contact's role/availability, and capturing a callback window or email. The persona MUST NOT state specific cost figures, make clinical recommendations, compare to specific competitors, or ask for / accept any PHI. This is a verbatim restatement of the Slice 1 allowed-claim policy in one canonical Slice 3 location; it adds nothing new.
- **Human-review reasons (Slice 1 + Slice 3, restated)** *(per R4-Q11)*: The complete `human_review_reason` enumeration is the Slice 1 set — `outside_allowed_claims`, `non_clinical_topic_escalation`, `phi_collection_risk`, `script_truncated`, `ambiguous_intent` — plus the single additive Slice 3 entry `shadow_stt_discrepancy` (FR-031). No Slice 1 reason is removed, renamed, or repurposed; the live model cannot expand this set (FR-014). Distinct from the **failure-reason vocabulary** (`live_call_abandonment`, `redaction_failed`, `dnc_write_failed`, `provider_error`, `runtime_crash`, `silence_timeout`). Per FR-013, a failure reason code does NOT bind to a single disposition: `provider_error` / `runtime_crash` / `silence_timeout` attach to a `failed` disposition ONLY when the call never reached the connected normalized state (and only `provider_error` / `runtime_crash` can do so — `silence_timeout` cannot occur pre-connection), and otherwise attach to a `needs_human_review` disposition with reason `script_truncated` once the call had connected. `live_call_abandonment` and `dnc_write_failed` / `redaction_failed` are recorded with the `failed` disposition. FR-013 is the operative mapping; this Definitions entry is descriptive of that mapping and does not override it. The failure-reason vocabulary is owned by the orchestrator / runtime (not the persona) and the live model MUST NOT emit or expand it, exactly as FR-014 protects the `human_review_reason` enumeration (per CHK145).

## Clarifications

### Session 2026-05-25

- Q: After the persona delivers the AI-on-behalf-of-Medx disclosure, what is the required behavior when the caller does NOT explicitly acknowledge it? → A: Continue the persona flow after a brief pause; treat absence of an opt-out as implicit acknowledgment (no escalation, no new audit flag, no new human-review reason).
- Q: Should Slice 3 persist raw call audio as a separate artifact alongside transcripts? → A: Out of scope for Slice 3 — defer raw-audio capture to a later slice with its own retention, consent, and redaction design. Slice 3 produces transcripts (live + shadow STT) only.
- Q: Should the invoking operator's identity be recorded for every real-call / write-enabled run? → A: Capture operator identity on the local session and run report only; do not propagate it into Dynamics.
- Q: Which signal MUST trigger orchestrator finalization with `needs_human_review` (`script_truncated`) or `failed` (runtime-failure) mid-call for "no usable signal" from the live runtime / model? → A: Any of (a) provider error from the configured real-time AI model, (b) Pipecat runtime crash, or (c) a configurable silence-after-connection / no-extraction-event timeout.
- Q: What behavior is required when two CLI invocations target the same Dataverse queue item simultaneously? → A: Reuse Slice 2 queue-claim semantics — the second invocation observes the item as not-`ready` (claimed / `in_progress`) and exits with a blocked-by-claim message; no SignalWire dial, no attempt consumed.

### Session 2026-05-25 (Round 2 — checklist-driven)

Round 2 was triggered by `/speckit-checklist` (max coverage / max depth) surfacing 4 [Conflict] markers and high-impact [Gap] clusters in `security.md`, `performance.md`, and the cross-cutting `requirements.md`. CHK012 (FR-036 / Key Entities Run Report field-list mismatch) and the 27-item performance-gap cluster were applied directly without questions (FR-036 amended to include `telephony_readiness_summary` + failure / blocked reason; a new "Performance and latency targets" subsection added under Deferred to Implementation Plan).

- Q: Behavior on resume when the original session received SignalWire `answered` but no normalized terminal event before orchestrator restart or persistent callback delivery failure? → A: Resume immediately finalizes the session as `failed` with reason `live_call_abandonment`; the Slice 2 resume / idempotency behavior applies for any partial write-back. (Resolves FR-022 ↔ FR-026 interplay.)
- Q: How does the orchestrator handle shadow STT lane processing that is still in-flight at the moment the orchestrator finalizes a connected-call session? → A: The orchestrator finalizes the session immediately (FR-029 non-blocking guarantee preserved), but the CRM write-back is held for a deployment-configurable grace window so a late shadow-STT discrepancy MAY participate in the disposition (FR-031 escalation rule); if the grace window elapses, write-back proceeds without the shadow result and any later shadow output is recorded as a post-finalization audit-only `shadow_lane_truncated` event. (Resolves FR-029 ↔ FR-031 interplay.)
- Q: Are DNC / opt-out (FR-024), blocked-status (FR-023), and dial-blocked (FR-012) field writes additional write-back operations beyond the Slice 2 four (Phone Call activity emission, queue-status update emission, Task emission, write-back assembly)? → A: No — they are field-level variants of the existing queue-status update emission operation; the operation count remains four and the FR-020 contract is preserved verbatim.
- Q: Required behavior for a SignalWire callback that fails authentication (FR-008 "MUST reject")? → A: Reject with the provider-appropriate HTTP code AND record the rejection in a distinct "rejected-by-authentication" audit log (separate from the duplicate / out-of-order callbacks audit log) containing `(received_at, source metadata)` but NOT the verification secret and NOT the callback body content; the run report MUST surface a rejected-by-authentication count.
- Q: Which artifacts MUST default-on transcript redaction (FR-033) cover beyond the full transcript file? → A: The full transcript file PLUS the session-result `summary`, the shadow STT transcript, and the shadow STT discrepancy records. Transcript pointer metadata is excluded (pointers MUST remain machine-readable for resume / inspection).
- Q: Required behavior when a caller volunteers PHI mid-call despite the persona refusing to collect it? → A: The persona MUST escalate `needs_human_review` with reason `phi_collection_risk` AND the default-on redaction policy MUST tag-and-redact the PHI-bearing utterance in the transcript, session-result summary, shadow STT transcript, and shadow STT discrepancy records before any of those artifacts are written to disk. The call MAY continue or end per the persona's existing decision rules.
- Q: Operator identity behavior on a resume run by a different operator than the original? → A: Preserve the original session's operator identity on the local session record and audit artifacts; record the resuming operator's identity separately on the run report (e.g., "resumed by X, original operator Y"); resume still requires the real-call / write-enabled flag.
- Q: Is the real-call / write-enabled flag required on every CLI invocation that performs a Dataverse mutation, including resume? → A: Yes — every Dataverse-mutating invocation MUST supply the flag; absence on a resume invocation runs the resume in rehearsal mode (no Dataverse mutation; surface what would have been written). No "sticky" or session-inherited promotion.
- Q: Write order requirement when a `do_not_call` (or mid-call opt-out) session reaches the write-back step? → A: The DNC / opt-out field write (FR-024) MUST be attempted FIRST in the write-back sequence — before the queue-status update, before the Phone Call activity, before any Task. If the DNC write succeeds and a later write fails within the retry budget, the contact is already protected from further outreach; idempotency-key stamping prevents duplicate DNC writes on resume.

### Session 2026-06-01 (Round 3 — checklist-gap closure)

Round 3 was triggered by a deep/wide reverify of all 17 requirements-quality checklists, which surfaced nine cross-cutting gap clusters. The decisions below close them; the affected FRs are amended inline.

- Q: How is the live-AI model identity represented in the run report (the `runtime_identity` object)? → A: As `model_name` + `model_version` (two fields), matching data-model §1.12 and the CLI contract. The single `model` field in research §9 was a drift and is corrected; there is exactly one canonical shape. (Closes the run-report schema-drift conflict.)
- Q: What bounds the `source_metadata` recorded for a rejected-by-authentication callback, and how are unassociatable (null-`session_id`) rejections surfaced and retained? → A: `source_metadata` is restricted to an explicit allow-list — provider-supplied source identifier(s) and remote IP / transport-level metadata only — capped in size (≤ 1 KB serialized, ≤ 16 keys); it MUST NOT contain caller-supplied body fields. Unassociatable rejections are written under `artifacts/_unassociated/` and counted in a deployment-level `rejected_auth_unassociated_count` surfaced by operator tooling; the `artifacts/_unassociated/` tree honors the same ≥ 90-day retention floor. On any signature-verification failure the receiver MUST drop the request body buffer without persisting it. (Closes the rejected-auth / `_unassociated` cluster.)
- Q: Is a shadow-lane *failure* (the lane never produced usable output / crashed / timed out) the same run-report signal as a *truncation* (late-after-grace-window output)? → A: No — they are distinct. The run report carries both `shadow_stt.lane_truncated` (late output) AND a new `shadow_stt.lane_failed` (the lane crashed or timed out and produced no usable result), recorded independently. (Closes the lane_failed vs lane_truncated gap.)
- Q: Is the post-finalization grace window value operator-visible, and what is the force-immediate-write path? → A: The in-effect `grace_window_sec` MUST be recorded on the session and surfaced in the run report. Setting `grace_window_sec = 0` is the supported force-immediate-write path (write-back proceeds without holding for the shadow lane; any later shadow output becomes a `shadow_lane_truncated` event). The default is deployment configuration (plan default 3s); there is no spec-mandated maximum. (Closes the grace-window operability gap.)
- Q: How is PHI redaction made observably distinct and testable, and what happens if the redaction pass fails? → A: The PHI tag-and-redact pass MUST replace the PHI-bearing span with the distinct marker `[PHI-REDACTED]` (distinguishable from the generic `[REDACTED]` marker), so the PHI-volunteered case is objectively detectable in artifacts. Redaction is **fail-closed**: if the default-on or PHI redaction pass raises or cannot complete for an artifact, that artifact MUST NOT be written in unredacted form; the session finalizes with a `redaction_failed` failure reason and the run report records it. (Closes the PHI redaction fail-mode + tag-marker gap.)
- Q: Which disposition wins when `phi_collection_risk` co-occurs with `do_not_call`, and what reason code wins when PHI is detected only by the shadow lane? → A: Safety-stop wins the final disposition: a clear opt-out / DNC yields `do_not_call` as the final disposition even when PHI was volunteered in the same call; `phi_collection_risk` is still recorded as an audit/review escalation overlay (and triggers tag-and-redact) but does not displace `do_not_call`. When PHI is surfaced only by the shadow lane, `phi_collection_risk` takes precedence over `shadow_stt_discrepancy` as the review-task reason code. A session that volunteers PHI in multiple utterances produces exactly one `phi_collection_risk` review Task. (Closes the PHI-volunteered precedence gap.)
- Q: What is the configuration precedence when the same non-secret setting is expressed in more than one place (CLI flag, env var, `config/slice3.toml`)? → A: Precedence is CLI flag > environment variable > `config/slice3.toml` > built-in default, for every overlapping non-secret setting (including the three timeouts and the shadow-STT toggle). Secrets remain env-var-only and have no TOML/CLI surface. (Closes the config-precedence gap.)
- Q: Which telephony readiness checks run on a resume invocation, and how is a 3-or-more operator resume chain recorded? → A: Resume never places a new dial in Slice 3 (one dial per session), so the pre-dial telephony readiness checks are NOT re-evaluated on resume; the run report labels each readiness check `skipped (resume)`. The operator-identity record preserves the full chain: `original` is the first authorizer (never overwritten), `current` is the latest resumer, and a `chain` array records every operator in order, so no intermediate resumer is dropped. (Closes the resume-readiness + operator-chain gap.)
- Q: Are telephony-consent / robocall regulatory frameworks (TCPA prior-express-consent, STIR/SHAKEN caller-ID attestation, two-party call-recording consent, external DNC-registry scrubbing) in scope for Slice 3? → A: No — they are explicitly OUT OF SCOPE for Slice 3 and deferred to a dedicated compliance-hardening PRD. Slice 3 enforces only the local call-window / internal-DNC / attempt eligibility rules (the six Slice 1 rules) plus the persona opt-out / DNC stop. This is a declared exclusion, not an oversight. (Closes the jurisdiction/consent gap; the Requirement Coverage Notes are also refreshed for the Round 2 additions.)

### Session 2026-06-01 (Round 4 — checklist residual closure)

Round 4 closes the 153 residual requirements-quality items surfaced by the Round 5 deep/wide reverify (items not in the Round 3 theme cluster). Decisions are grouped by domain; affected FRs / Definitions / Deferred / Assumptions are amended inline. Decisions tagged **[OUT OF SCOPE]** are declared exclusions, not oversights.

**Configuration & pre-dial readiness**
- R4-Q1: Missing real-time AI provider credentials at invocation → FR-009 readiness adds a `realtime_ai_credentials` check (fails before dial, exit 4, no attempt). Missing shadow-STT credentials: when shadow is explicitly enabled via `--shadow-stt`, FR-009 adds a `shadow_stt_credentials` check that fails the run; when shadow is only default-on-from-config, a missing key disables the lane with a run-report warning rather than blocking the demonstrable loop (FR-032 "loop completes without it").
- R4-Q2: `[retention].mode` omitted → defaults to `full_with_redaction`. `discrepancy_policy_path` missing/malformed while shadow enabled → refuse-to-start (exit 4) with a named readiness failure; never silently treat all discrepancies as benign or all as uncertain.
- R4-Q3: Callback-URL templates honor exactly the `{session_id}` placeholder; any other placeholder is a config error surfaced at readiness (exit 4).
- R4-Q4: Selecting fixture-replay vs the real SignalWire transport is a non-secret `[signalwire].transport = "real" | "fixture"` setting (default `real`); the fixture path is debug-only.

**Error handling & exit codes**
- R4-Q5: `RealtimeProviderError` carries `transient: bool`; a transient pre-connection provider error is retried within the connect budget, a terminal one finalizes per FR-013. Mid-call, ANY provider error is a degradation trigger per FR-013 regardless of `transient`.
- R4-Q6: Run-level disposition vs retry: a successful retry keeps the persona disposition; an exhausted write-back retry budget leaves the persona disposition intact and marks the unfinished operations `resume-needed` — the disposition is NEVER overwritten with `failed` due to a write-back retry exhaustion.
- R4-Q7: If the DNC-first write itself exhausts its retry budget, the run halts the remaining write-back, finalizes with failure reason `dnc_write_failed`, emits a prominent operator alert (the contact may be unprotected), and the resume path retries DNC-first.
- R4-Q8: A resume invocation that finalizes a previously-abandoned session exits `6` (live-call abandonment), not `0`.
- R4-Q9: Exit `1` (unexpected) maps any uncaught exception after redaction-safe logging; exit `2` (bad usage) ALWAYS emits an operator message naming the offending/missing argument. Quickstart §8 documents remedies for exit `1` and `2`.

**Persona safety**
- R4-Q10: "brief pause" after the disclosure = a deployment-configurable `disclosure_pause_ms` (default 1500 ms); absence of a clear opt-out within it is implicit acknowledgment (FR-015 otherwise unchanged).
- R4-Q11: The positive allowed-claim set AND the full Slice 1 `human_review_reason` enumeration are restated in one canonical Slice 3 location (§Definitions "Allowed claims (Slice 1, restated)" and "Human-review reasons (Slice 1 + Slice 3)") rather than only cross-referenced.
- R4-Q12: On resume, `runtime_identity` is PRESERVED from the original session (the live runtime does not re-run on resume — there is no new call), exactly as operator-identity `original` is preserved (FR-016); the resuming invocation does not overwrite it.

**Observability**
- R4-Q13: FR-013 runtime-failure reasons are enumerated as distinct run-report reason codes — `provider_error`, `runtime_crash`, `silence_timeout` — so the report distinguishes the three FR-013 triggers.
- R4-Q14: The run report carries the live-call abandonment timeout value (`abandonment_timeout_sec`) and, on abandonment, the elapsed condition; and a shadow-lane failure detail `{failure_type, at}` alongside `shadow_stt.lane_failed`.
- R4-Q15: `shadow_stt.discrepancy_summary` has a defined shape: `{fields_compared, discrepancies, uncertain, per_field:[{field, classification}]}` (counts + per-field classification), not a free-form string.
- R4-Q16: Provider-account identifiers (SignalWire project id, real-time provider account/org id) are EXCLUDED from the recorded runtime/model config (only provider name + `model_name`/`model_version`), alongside the existing credential exclusion (FR-016 / FR-035).

**Security**
- R4-Q17: The no-secrets guarantee (FR-035) EXTENDS to exception messages and stack traces, not just logs/exported artifacts; the global exception handler redacts before any write.
- R4-Q18: Disabling default-on redaction entirely is permitted ONLY via explicit `[redaction].policy = "disabled"`, which MUST emit a prominent startup + run-report warning; redaction is never silently off.
- R4-Q19: A callback is "unassociatable" when its `{session_id}` URL path segment matches no known session row (or is absent) → null `session_id` → `artifacts/_unassociated/`.
- R4-Q20: The signing secret is loaded from the environment ONLY, at signature-module init; loading from disk or argv is forbidden (reinforces FR-035).
- R4-Q21: SC-018's no-secrets gate applies generically to ALL artifact classes (a class-agnostic sweep), not a fixed file-glob.
- R4-Q22: **[OUT OF SCOPE]** Replay/nonce hardening beyond signature verification + `(session_id, provider_event_id)` dedup (timestamp-window / nonce store) is deferred to the compliance-hardening PRD.
- R4-Q23: FR-008 "where supported": if a deployment cannot supply callback signature verification, the run refuses to start in real-call mode (fail-closed) with a named readiness failure — there is no unauthenticated-callback fallback.
- R4-Q24: Slice 3 authenticates ONLY SignalWire status/media callbacks; no other inbound integration callback exists in scope (stated explicitly).

**Idempotency / data model**
- R4-Q25: data-model §3 adds `CallEvent` + `CallbacksAuditLog` table DDL; `CallEvent` carries a UNIQUE constraint on `(session_id, provider_event_id)` so dedup is schema-enforced, not application-only.
- R4-Q26: The DNC / queue-status field-update dedup reads the `writeback_progress` ledger (not the live Dataverse field value) so resume is deterministic and cannot diverge across re-invocations.
- R4-Q27: The rejected-auth audit log is append-one-row-per-delivery (every forged delivery recorded; no dedup) — each attempt is independently security-relevant; null-session duplicates are each recorded.

**Acceptance Scenarios**:

1. **Given** a transient Dataverse error during Phone Call activity creation, **When** the bounded in-run retry budget completes, **Then** the retry succeeds without creating a duplicate Phone Call activity (Slice 2 retry / idempotency key behavior reused).
2. **Given** the in-run retry budget is exhausted after one CRM write succeeded but a later write failed, **When** the operator re-invokes the CLI for the same session, **Then** the run resumes only the missing writes and creates no duplicate of any already-written CRM record.
3. **Given** SignalWire retries delivering a status callback after a transient failure, **When** the second delivery arrives, **Then** it is treated as a duplicate of the same provider event id and is a no-op for state, attempt count, and write-back, but is recorded in the callbacks audit log.
4. **Given** the orchestrator process restarts between SignalWire's `completed` callback and Dataverse write-back, **When** the operator re-invokes the CLI for the same session, **Then** the run resumes only the missing CRM writes and the recorded real provider call ID is preserved.
5. **Given** a `needs_human_review` outcome where the review Task creation fails transiently, **When** the retry / resume path runs, **Then** Dynamics ends with exactly one review Task assigned to the configured review owner with the correct reason code.

### Edge Cases

- **SignalWire status callback delivered after disposition finalized**: A duplicate or late status callback (e.g., `failed` after `completed`) MUST NOT change the finalized disposition, MUST NOT mutate the normalized result, MUST NOT increment `attempt_count`, and MUST NOT emit a new CRM write-back payload. The conflicting callback MUST be recorded in the local audit log keyed by `(session_id, provider_event_id)`, consistent with Slice 1's `conflicting_events` audit-channel behavior.
- **SignalWire status callbacks delivered out of order**: The transport adapter MUST be tolerant of out-of-order delivery (e.g., `completed` arriving before `answered`) and MUST normalize the stream into a coherent disposition. The orchestrator MUST NOT rely on strict ordering of intermediate status callbacks.
- **Duplicate SignalWire media callback**: Treated as a duplicate event keyed by provider event id; the Pipecat runtime is wired exactly once per session; the second media callback is a no-op.
- **Live-call abandonment / orchestrator crash mid-call**: If the orchestrator terminates or the SignalWire callback delivery fails persistently after a successful dial, the session MUST NOT remain in `in_progress` indefinitely. After the configured live-call abandonment timeout the session is finalized as `failed` with a `live_call_abandonment` reason; no false connected-call Phone Call activity is created if the call never reached a normalized connected state; the Slice 2 resume path applies for any partial write-back.
- **Mid-call opt-out / DNC**: Same Slice 1 behavior — persona stops the sales flow before any further sales utterance; final disposition is `do_not_call`; Dataverse DNC / opt-out and queue-status fields are updated; no callback or review Task is created. Carries over verbatim to the live Pipecat path.
- **Mid-call PHI / out-of-allowed-claim attempt by the live model or the contact**: Persona escalates with `needs_human_review` using the appropriate enumerated reason (`phi_collection_risk`, `non_clinical_topic_escalation`, or `outside_allowed_claims`), the conversation ends safely (or may continue per the persona's decision rules in the PHI-volunteered case), and one review Task is created in Dynamics with the reason code. When the trigger is caller-volunteered PHI (the contact volunteers PHI despite the persona refusing to ask for or accept it), the persona MUST escalate `phi_collection_risk` AND the default-on redaction policy MUST tag-and-redact the PHI-bearing utterance in the full transcript, the session-result summary, the shadow STT transcript, and the shadow STT discrepancy records before they are written to disk (per FR-015, FR-033).
- **Live model failure or runtime crash mid-call**: The orchestrator MUST treat any of (a) an explicit error from the configured real-time AI model provider, (b) a Pipecat runtime crash or unrecoverable adapter failure, or (c) elapse of the deployment-configurable silence-after-connection / no-extraction-event timeout as a live-runtime degradation trigger per FR-013. After the call connected, any of (a) / (b) / (c) finalizes the session as `needs_human_review` with reason `script_truncated`. Before the connected normalized state, (a) and (b) finalize the session as `failed` with a runtime-failure reason and no connected-call Phone Call activity is created; trigger (c) is not applicable before connection because the silence timer only starts after connection.
- **Real-dial phone-number validation failure**: A missing, blank, or malformed destination phone number MUST block before any SignalWire dial, MUST NOT consume an attempt, MUST NOT create a Phone Call activity, and MUST surface the failure in the readiness report. Promotes the Slice 2 non-E.164 data-quality warning to a hard Slice 3 pre-dial block.
- **SignalWire credentials or source number unauthorized / suspended mid-run**: Treated as a telephony readiness failure on the next pre-dial check; in-flight calls are allowed to complete (the suspension event MUST NOT terminate a connected call early just to satisfy the readiness check).
- **Status / media callback URL unreachable from SignalWire side**: Detected by the readiness check (when configured), or detected at run time as missing callbacks; missing callbacks for a placed call fall under live-call abandonment behavior.
- **Provider 4xx on dial request (e.g., invalid number, blocked, unauthorized)**: No attempt is consumed; no Phone Call activity is created; the run exits with a provider-rejected-dial failure recorded in the run report; the queue-status update reflects the dial-blocked outcome per the existing per-disposition mapping for blocked / failed cases.
- **Partial CRM write-back after a real call**: Same Slice 2 behavior — bounded in-run retry, idempotency-key stamping, resume on re-invocation; never creates a duplicate Phone Call activity or Task.
- **Shadow STT mismatch on a high-value field**: Recorded as a discrepancy event under the session, MUST NOT block the live call, MUST NOT independently write a CRM record, and MUST NOT override the final disposition in the MVP. If the discrepancy policy classifies the mismatch as uncertain, the orchestrator escalates to `needs_human_review` with a `shadow_stt_discrepancy` reason.
- **Shadow STT lane fails or times out**: The live call continues unaffected; the run report records the shadow-lane failure; no discrepancy events are emitted for the missing-shadow case.
- **Transcript retention is summary-only or pointer-only**: No full transcript file is written; the session-result artifact still includes the normalized summary, retention mode, and persona version. The shadow STT artifact follows the same retention policy. Default-on redaction still applies whenever a full transcript file would otherwise be written.
- **Default-on redaction applied to a Slice 3 transcript**: Redaction runs before any transcript artifact is written to disk. Logs and exported artifacts MUST NOT contain secrets.
- **Dataverse metadata drift detected between rehearsal and real-call run**: The real-call / write-enabled run's live verification fails and the run exits before dial — reusing Slice 2's lightweight live verification behavior unchanged.
- **CRM queue item changed by a human between claim and write-back during a real call**: Same Slice 2 conflict-detection behavior — preserve high-confidence values, stop the write-back before the final status update on a detected conflict, and finalize the session as `needs_human_review` (the conflict is reported for human review via the same review-Task path; the session is NOT left open and is NOT finalized as `failed`). The persona's extracted-state disposition is preserved on the local session record for the reviewer, but the run's final disposition for the conflicted write-back is `needs_human_review` so the stopped write-back is operator-visible and recoverable.
- **Concurrent CLI invocation on the same Dataverse queue item**: The second invocation observes the item as not-`ready` via the Slice 2 queue-claim semantics and exits before dial with a blocked-by-claim message. No SignalWire call is placed, no attempt is consumed, no Phone Call activity or Task is created by the second invocation, and the first invocation is unaffected. Multi-worker coordination remains out of scope; the queue-claim observation is the only Slice 3 contract.
- **Resume after a real call when retention policy disables the transcript artifact**: The resume path runs the missing CRM writes from local audit artifacts; the absence of a transcript file is not an error; the planned/actual write-back payloads, run report, and CRM correlation rows remain authoritative for resume.

### Functional Requirements

#### Real-call / write-enabled run mode and defaults

- **FR-001**: The system MUST require an explicit real-call / write-enabled flag (or equivalent deliberate action) before placing a SignalWire dial or mutating Dataverse. The CLI default invocation MUST NOT place a SignalWire call and MUST NOT mutate Dynamics — the Slice 2 dry-run default is preserved and extended so that absence of the real-call / write-enabled flag also blocks SignalWire dialing.
- **FR-002**: The system MUST provide a rehearsal / readiness mode that verifies Dataverse mapping, SignalWire telephony readiness, destination phone format, persona/runtime configuration, eligibility, and the planned dial plan and write-back payloads, and produces a readiness report plus planned write-back artifacts — without placing a SignalWire call and without creating or updating any Dataverse record beyond approved dry-run behavior. Rehearsal / readiness mode MUST be the default behavior when the real-call / write-enabled flag is omitted. Rehearsal / readiness mode is **configuration-only with respect to the live runtime**: it verifies the persona/runtime CONFIGURATION (credentials presence, model/provider identity, persona-version provenance, dial-plan and write-back payload assembly) but MUST NOT invoke the Pipecat runtime or the configured real-time AI model against audio, and MUST NOT place a SignalWire dial — there is no live-model or recorded-audio playback in rehearsal mode. (A recorded-audio replay harness through the Pipecat runtime is a test-posture concern, not a rehearsal-mode behavior; see §Deferred "Test posture for real calls".) (per testing-strategy CHK010).
- **FR-003**: The system MUST process exactly one Dataverse queue item per invocation. Batch calling, schedulers, campaign automation loops, multi-worker coordination, and distributed job queues remain out of scope for Slice 3. Required operator inputs are the campaign selector, the queue-item selector, the persona/runtime configuration, the SignalWire configuration, and the run mode. When two CLI invocations target the same Dataverse queue item simultaneously, the system MUST reuse the Slice 2 queue-claim semantics: the second invocation MUST observe the queue item as not-`ready` (e.g., claimed / `in_progress`) and MUST exit before dial with an operator-visible blocked-by-claim message; the second invocation MUST NOT place a SignalWire call, MUST NOT consume an attempt, and MUST NOT create a Phone Call activity or Task. The first invocation is unaffected by the second invocation's exit. The queue-claim dedup key is the **Dataverse queue-item identifier** (the `--queue-item-id` selector's resolved record id), NOT the openCloser session ID: claim contention is observed on the queue item itself, so two distinct sessions targeting the same queue item contend, while a single session's resume re-invocation (which carries the original session id) does not self-block. The concurrent-claim block is a pre-dial gate that precedes the telephony readiness stage and carries the same no-dial / no-attempt / no-Phone-Call-activity guarantees as a telephony readiness failure (per idempotency CHK075 and telephony-readiness CHK130).

#### Real SignalWire outbound dialing

- **FR-004**: The system MUST add a real SignalWire outbound dialing transport adapter that satisfies the existing call-transport conceptual contract (the same `place_call(queue_item, dial_plan) → provider_call_id` and event-stream surface proven in Slice 1) and is the only path through which call-level events for real calls enter the Interaction Core.
- **FR-005**: The SignalWire transport MUST translate SignalWire provider states and webhook callbacks into the existing normalized openCloser event set — `connected`, `no_answer`, `voicemail`, `failed`, `completed` (and `callback_requested`, which remains part of the normalized event vocabulary but is **not** produced by SignalWire call-status normalization — the callback-request outcome is a persona-determined disposition (`interested_callback_requested`), not a transport call-status event) — and MUST be tolerant of out-of-order, duplicate, and late-after-finalization provider callbacks. SignalWire provider-specific event shapes, intermediate status names, and carrier failure subtypes MUST be mapped inside the transport adapter and MUST NOT leak into the orchestrator, eligibility evaluator, persona, or Dataverse adapter.
- **FR-006**: The system MUST assign a real provider call ID per dialed call attempt and MUST record it on the session. The real provider call ID is recorded in the normalized session result field previously named "mock provider call ID" in Slices 1 and 2 (renamed for Slice 3 while remaining backwards-compatible with the Slice 1 / Slice 2 correlation behavior for replay / audit inspection of pre-Slice-3 sessions).
- **FR-007**: The system MUST handle SignalWire status and media callbacks needed for the MVP real-call path: at minimum, status callbacks for ringing / answered / in-progress / completed / no-answer / voicemail / busy / canceled / failed (or carrier-equivalents) and media callbacks for the connected media stream lifecycle. The transport adapter MUST de-duplicate callbacks by SignalWire-provided event identity and MUST record every callback (including duplicates) in the local callbacks audit log keyed by `(session_id, provider_event_id)`.
- **FR-008**: The system MUST authenticate SignalWire callback delivery using the provider's documented mechanism where supported (e.g., signature verification), MUST reject callbacks that fail authentication with the provider-appropriate HTTP response code, and MUST NOT log secrets associated with the verification mechanism. The "where supported" caveat is fail-closed (R4-Q23): a deployment that CANNOT supply callback signature verification MUST refuse to start in real-call mode, surfaced as the named `signing_secret_verifiable` telephony readiness failure (FR-009) — there is NO unauthenticated-callback fallback. This refuse-to-start consequence is a distinct compliance requirement (the strongest authentication-posture guarantee in Slice 3): an unverifiable-signature deployment cannot place a real call at all (per compliance CHK156). Every rejected-by-authentication callback MUST be recorded in a distinct rejected-by-authentication audit log (separate from the duplicate / out-of-order callbacks audit log) containing at minimum `(received_at, source metadata)` — for example provider-supplied source identifiers or IP-level metadata where available — and MUST NOT include the verification secret and MUST NOT include the callback body content (defense in depth against reflected-payload leakage). The recorded `source_metadata` MUST be restricted to an explicit allow-list of non-caller-controlled fields (provider-supplied source identifier(s) and remote IP / transport-level metadata only) and MUST be bounded in size (≤ 1 KB serialized, ≤ 16 keys) so a forged callback cannot stuff arbitrary payload into the audit log. On any signature-verification failure the receiver MUST drop the request body buffer without persisting it. A rejected callback that cannot be associated with a known session (null `session_id`) MUST still be recorded under `artifacts/_unassociated/`, which MUST honor the same ≥ 90-day local-artifact retention floor as session-scoped artifacts. The run report MUST surface the count of rejected-by-authentication callbacks for the session (per FR-036), and operator tooling MUST surface a deployment-level `rejected_auth_unassociated_count` for the null-session rejections, so operators can detect attempted forgeries even when they target no known session.

#### Telephony readiness and pre-dial gates

- **FR-009**: The system MUST enforce a hard telephony readiness check before any real-call / write-enabled SignalWire dial. The check MUST verify, at minimum: SignalWire credentials present and validatable; the SignalWire callback signing secret present and loadable (so callback signature verification can run — per FR-008 / R4-Q23, a deployment that cannot verify signatures MUST fail this check and refuse to start in real-call mode); configured source caller-ID number present and authorized for outbound dialing (the "authorized" check is the SignalWire-side provider authorization of the source caller-id, per R4-Q48); real-time AI provider credentials present (`realtime_ai_credentials`, per R4-Q1); shadow-STT provider credentials present when shadow STT is explicitly enabled via `--shadow-stt` (`shadow_stt_credentials`, per R4-Q1 — when shadow is only default-on-from-config, a missing key disables the lane with a run-report warning instead of failing the run); destination phone number present and passing E.164 / provider-acceptable validation per FR-010; SignalWire status and media callback URLs configured with only the supported `{session_id}` placeholder (any other placeholder is a readiness failure per R4-Q3) and reachable when reachability is verifiable in the deployment; campaign-to-persona/runtime mapping resolved; verified Dataverse mapping (reusing the Slice 2 live verification gate, extended per R4-Q34 to confirm Dynamics accepts the `shadow_stt_discrepancy` review-task reason value); the shadow STT discrepancy-policy file present and parseable when shadow STT is enabled (missing/malformed → readiness failure per R4-Q2); callback and review Task owner/team mapping resolved; and local call-window / DNC / attempt eligibility (the six Slice 1 eligibility rules) allowing the call.

  **Authoritative readiness-check list (CHK123).** The post-R4 telephony readiness check set is the following authoritative enumeration; the earlier "eight readiness checks" framing (in the Definitions, the User Story 3 Independent Test (a)–(h), and SC-010) is the original Slice 1-derived subset and is superseded by this fuller list, which is the single source of truth for the total: (1) `signalwire_credentials`; (2) `signing_secret_verifiable` (signing secret present and loadable; refuse-to-start in real-call mode if signatures cannot be verified, R4-Q23); (3) `source_number_authorized`; (4) `realtime_ai_credentials` (R4-Q1); (5) `shadow_stt_credentials` (R4-Q1, conditional — see below); (6) `destination_phone_valid` (FR-010); (7) `status_callback_url_configured`; (8) `media_callback_url_configured`; (9) `callback_url_placeholder_valid` (R4-Q3); (10) `campaign_persona_runtime_mapping_resolved`; (11) `dataverse_metadata_verified`; (12) `dataverse_accepts_shadow_discrepancy_reason` (R4-Q34); (13) `shadow_discrepancy_policy_loadable` (R4-Q2, conditional — see below); (14) `callback_review_owner_mapping_resolved`; (15) `eligibility_allows_call` (the six Slice 1 eligibility rules). The data-model §1.9 `check_name` enum is the machine-readable form of this list and MUST match it one-to-one.

  **Each readiness check is an individually testable, distinct failure category (CHK124).** Each of the six R4-added checks — `signing_secret_verifiable`, `realtime_ai_credentials`, `shadow_stt_credentials`, `shadow_discrepancy_policy_loadable`, `callback_url_placeholder_valid`, `dataverse_accepts_shadow_discrepancy_reason` — maps one-to-one to a distinct §1.9 `check_name` enum value and to the telephony-readiness-failure exit (exit 4), and MUST each be independently exercisable to that exit exactly as the original checks are. No R4-added check is folded into another check's pass/fail.

  **`shadow_stt_credentials` is the only flag-conditional tri-state check (CHK125-readiness).** `shadow_stt_credentials` fails the run (exit 4) ONLY when shadow STT is explicitly enabled via `--shadow-stt` and the credential is missing; when shadow STT is merely default-on-from-config, a missing credential DISABLES the lane with a non-blocking run-report WARNING (degraded mode) rather than failing readiness. This flag-conditional pass/fail/warn tri-state is unique to `shadow_stt_credentials` among the readiness checks. The run report MUST distinguish the "shadow disabled with a missing-credential warning" outcome from a clean shadow-disabled run (the warning is recorded; a clean disabled run carries no warning).

  **`shadow_discrepancy_policy_loadable` failure surface (CHK126).** This check is conditioned on shadow STT being enabled: when shadow STT is enabled and the discrepancy-policy file is missing OR malformed, the check fails the run (exit 4) with a named failing-check detail; the run MUST NOT silently treat all discrepancies as benign or all as uncertain. When shadow STT is disabled, the check does not apply.

  **`callback_url_placeholder_valid` is distinct from URL configuration / reachability (CHK127).** The callback-URL templates MUST honor EXACTLY the `{session_id}` placeholder; ANY other placeholder is a placeholder-validity readiness failure (exit 4). This `callback_url_placeholder_valid` failure category is separate and independently named from the `status_callback_url_configured` / `media_callback_url_configured` configuration / reachability checks, so an operator can tell a placeholder error from an unreachable-or-missing-URL error.

  **`dataverse_accepts_shadow_discrepancy_reason` relationship to `dataverse_metadata_verified` (CHK128).** The `dataverse_accepts_shadow_discrepancy_reason` check (R4-Q34) is an extension of the Slice 2 Dataverse-metadata-verification gate that additionally confirms Dynamics accepts the `shadow_stt_discrepancy` review-task reason option-set value. It is an INDEPENDENTLY-failing `check_name` enum value, NOT a silent sub-step of `dataverse_metadata_verified`: `dataverse_metadata_verified` can PASS (the base mapping is valid) while `dataverse_accepts_shadow_discrepancy_reason` FAILS (the option-set value is not yet present in Dynamics), and the readiness report names whichever of the two failed.

  **Pre-dial gate ordering and exit-code routing (CHK130, CHK131).** Two gates PRECEDE the telephony readiness stage and carry the same no-dial / no-attempt / no-Phone-Call-activity guarantees as a readiness failure: the concurrent-claim block (exit 3, per FR-003) and the pre-dial Dataverse metadata-verification gate when Dataverse is unreachable at start (exit 7, per FR-022). A Dataverse-UNREACHABLE-at-start condition routes to exit 7 (the pre-readiness verification gate aborts the run before the readiness stage is entered), whereas a Dataverse mapping that is REACHABLE but fails the `dataverse_metadata_verified` / `dataverse_accepts_shadow_discrepancy_reason` readiness check routes to exit 4 (a readiness failure). The two conditions are disjoint: unreachable → exit 7 (separate gate); reachable-but-invalid-mapping → exit 4 (readiness failure). This ordering lets an operator distinguish a concurrent-claim block (exit 3), a Dataverse-unreachable abort (exit 7), and a telephony readiness failure (exit 4).
- **FR-010**: The system MUST validate the destination phone number against E.164 or a provider-acceptable equivalent before placing a SignalWire call. A missing, blank, or malformed destination phone number MUST block before the dial, MUST NOT consume an attempt, MUST NOT create a Phone Call activity, and MUST surface the failure in the readiness report. This promotes the Slice 2 non-E.164 data-quality warning to a hard Slice 3 pre-dial block.
- **FR-011**: A telephony readiness failure MUST exit the run before placing a SignalWire call, MUST NOT consume an attempt, MUST NOT create a Phone Call activity, and MUST NOT advance the Dataverse queue beyond the approved blocked-status write (or leave the queue unchanged for non-eligibility readiness failures), and MUST surface the failure in the readiness report with the failing check named.
- **FR-012**: A provider-rejected dial request (e.g., SignalWire returns a 4xx before the call is placed for an invalid / blocked / unauthorized number) MUST NOT consume an attempt, MUST NOT create a Phone Call activity, MUST be recorded in the run report as a provider-rejected-dial failure, and MUST advance the Dataverse queue per the existing per-disposition mapping for blocked / failed cases.

#### Live Pipecat runtime and configured real-time AI provider

- **FR-013**: The system MUST add a Pipecat real-time audio runtime adapter that satisfies the existing persona conceptual contract (`run(session_context, conversation) → PersonaOutput`) and bridges connected-call audio to and from the configured real-time AI model provider as the primary live conversation path. Pipecat-specific pipeline shapes, real-time AI model provider streaming protocols, and audio codec details MUST be confined to the runtime adapter and MUST NOT leak into the orchestrator, eligibility evaluator, transport, persona module (other than its existing inputs / outputs), or Dataverse adapter. The orchestrator MUST detect live-runtime degradation mid-call and finalize the session accordingly when ANY of the following triggers occur: (a) an explicit error from the configured real-time AI model provider, (b) a Pipecat runtime crash or unrecoverable adapter failure, or (c) a deployment-configurable silence-after-connection / no-extraction-event timeout elapses without progress. Triggers (a) and (b) finalize the session as `failed` with a runtime-failure reason when the call never reached a connected normalized state, or `needs_human_review` with reason `script_truncated` when the call had connected and the persona had begun the disclosed conversation; trigger (c) finalizes the session as `needs_human_review` with reason `script_truncated`. The silence-timeout default value is deployment configuration and is not pinned in this specification. The three triggers MUST be recorded in the run report as DISTINCT failure-reason codes — `provider_error` (a), `runtime_crash` (b), `silence_timeout` (c) — so observability can tell them apart (R4-Q13). The `RealtimeProviderError` carries a `transient` flag (R4-Q5): a transient PRE-connection provider error is retried within the connect budget; a terminal one finalizes immediately; once the call has connected, ANY provider error is a degradation trigger regardless of `transient`.
- **FR-014**: The ALF appointment-setter persona module MUST continue to own disclosure language, allowed claims, extraction schema, deterministic disposition rules, and escalation reasons. The live model MAY produce conversation turns and extraction events, but the persona's deterministic disposition precedence (the Slice 1 FR-036 rules) MUST select the final disposition; the live model MUST NOT change which disposition is selected for a given extracted state. The persona's enumerated `needs_human_review` reason set (Slice 1 FR-035) MUST NOT be expanded or replaced by the live model. The persona module's deterministic authority is bidirectional: the live model MUST NOT change which disposition is selected for a given extracted state AND MUST NOT veto, block, or suppress a disposition the deterministic rules select — the deterministic precedence is authoritative in both directions (per persona-safety CHK037). The opt-out / DNC trigger keyword set is owned by the persona module and is immune to live-model alteration: the live model MUST NOT introduce, remove, or alter an opt-out / DNC trigger keyword, and MUST NOT cause a caller opt-out matching the persona's enumerated trigger set to be missed or a non-trigger phrase to be treated as an opt-out — the enumerated Slice 1 opt-out / DNC trigger set is the sole authority for opt-out detection (per persona-safety CHK031). The disclosure language is owned solely by the persona module (this FR); the `disclosure_policy_version` / `disclosure_policy_hash` recorded in the run report's config-identity block (R4-Q46, FR-036) is an audit version/hash OF that persona-owned disclosure language — it is NOT a second, independent disclosure-language owner outside the persona module, and a reader MUST NOT infer split disclosure-language ownership from its presence in the config-identity block (per persona-safety CHK144). The non-clinical, no-PHI persona-safety constraints in this FR and in FR-015 are governed by the §Assumptions "Compliance scope" assumption (Slice 3 is a non-clinical ALF business-outreach demo, not a HIPAA-class clinical workflow); the persona-safety requirements MUST be read against that scope and the FR-015 PHI handling rule MUST NOT be misread as a clinical-workflow concession (per persona-safety CHK025). For the Slice 3 collisions the deterministic precedence is stated explicitly: (a) a clear opt-out / DNC MUST select `do_not_call` as the FINAL disposition even when PHI was volunteered in the same call — the safety-stop outcome outranks every other signal — while `phi_collection_risk` is still recorded as an audit/review escalation overlay (and triggers tag-and-redact per FR-015) without displacing `do_not_call`; (b) when PHI is surfaced only by the shadow STT lane, the `phi_collection_risk` reason code takes precedence over `shadow_stt_discrepancy` for the review Task; (c) a session that volunteers PHI across multiple utterances MUST produce exactly one `phi_collection_risk` review Task, not one per utterance.
- **FR-015**: The persona's first connected-call utterance MUST continue to deliver the canonical Slice 1 AI-on-behalf-of-Medx disclosure on every connected call. The persona MUST remain non-clinical, MUST NOT collect PHI, MUST honor immediate opt-out / DNC, MUST stay within the allowed-claim categories, and MUST escalate with `needs_human_review` using the Slice 1 enumerated reason codes when an out-of-allowed-claim, PHI, or out-of-scope topic is detected by the persona or attempted by the live model. The disclosure does NOT require an explicit verbal acknowledgment from the caller: in the absence of a clear opt-out / DNC statement, the persona MUST continue the conversation after a brief pause — a deployment-configurable `disclosure_pause_ms` (default 1500 ms, per R4-Q10) — and treat the absence of an opt-out within that window as implicit acknowledgment. No new `human_review_reason` is introduced for a missing acknowledgment; the existing Slice 1 enumerated reason set is unchanged for Slice 3 except for the additive `shadow_stt_discrepancy` entry. When a caller VOLUNTEERS PHI mid-call despite the persona refusing to ask for or accept it, the persona MUST escalate the session with `needs_human_review` reason `phi_collection_risk` AND the default-on redaction policy (FR-033) MUST tag-and-redact the PHI-bearing utterance in the full transcript, the session-result summary, the shadow STT transcript, and the shadow STT discrepancy records before any of those artifacts are written to disk. The PHI tag-and-redact pass MUST replace the PHI-bearing span with the distinct marker `[PHI-REDACTED]` (distinguishable from the generic `[REDACTED]` marker used by the default-on policy) so the PHI-volunteered case is objectively detectable in the artifacts. Redaction MUST be **fail-closed**: if the default-on or PHI redaction pass raises or cannot complete for an artifact, that artifact MUST NOT be written in unredacted form — the session finalizes with a `redaction_failed` failure reason recorded in the run report rather than writing unredacted content. When `redaction_failed` co-occurs with a content-bearing disposition (e.g., a connected call that yielded `do_not_call` or `needs_human_review` before the redaction pass failed), the `redaction_failed` outcome takes precedence and the session's final disposition is `failed` with reason `redaction_failed`, with the underlying content disposition preserved on the local session record as an overlay for the reviewer — fail-closed redaction is a safety stop that MUST NOT be silently downgraded to allow an unredacted write (per CHK136). On a `redaction_failed` finalize, the CRM write-back MUST HALT (no Phone Call activity, no queue-status update, no Task), parallel to the `dnc_write_failed` halt in FR-024 — with one exception: when the failing call was a `do_not_call` (or mid-call opt-out), the contact-protecting DNC-first field write (FR-024) MUST still be attempted FIRST so the contact is protected from further automated outreach even though the transcript artifact could not be safely written; only after the DNC-first write does the remaining write-back halt (per CHK137). The call MAY continue or end per the persona's existing decision rules; the PHI-volunteered case MUST be observably distinct from a non-PHI call in the audit artifacts and the run report. The specific continue-vs-end branch the persona takes on a PHI-volunteered event is **Deferred to Implementation Plan** (it inherits the Slice 1 persona decision rules): the branch chosen MUST NOT alter the finalized disposition — the `phi_collection_risk` escalation, tag-and-redact, and exactly-one review Task outcomes are pinned regardless of which branch is taken — so the continue/end choice is an execution-level decision and is intentionally not pinned here (per CHK103).
- **FR-016**: The persona version, the runtime/model identity, the model configuration relevant to audit (e.g., model name and version), and the invoking operator identity (at minimum the OS user or a CLI-provided operator identifier) MUST be recorded on every Slice 3 session and on the run report so that runs are reproducible and auditable. The `persona_version` is the pinned persona-policy version (the identifier of the deterministic persona policy / disclosure / extraction / disposition rule set) in effect for the session; recording it is the binding requirement, and the same `persona_version` MUST be recorded on EVERY Slice 3 session including rehearsal / readiness-mode runs and blocked-before-runtime runs, so a rehearsal artifact carries the same persona-version provenance as a real-call run and two runs that used different persona policies are distinguishable in audit (per persona-safety CHK059, CHK060). The scheme by which `persona_version` is incremented or pinned across persona-policy changes (versioning convention, monotonicity, hash derivation) is **Deferred to Implementation Plan** — the spec requires the version be recorded and be distinguishing; the increment policy is a plan-side decision (per persona-safety CHK059). The operator identity MUST be recorded on the local session and run report only and MUST NOT be propagated into Dataverse (no new Phone Call activity / queue / Task field is added for operator identity; the Slice 2 Dataverse mapping surface is unchanged). On a resume invocation, the original session's operator identity MUST be preserved on the local session record and the audit artifacts (the original authorizer is not overwritten); the resuming operator's identity MUST be recorded separately on the run report (e.g., "resumed by X, original operator Y"). When a session is resumed more than once by different operators, the run report MUST preserve the FULL operator chain — `original` is the first authorizer (never overwritten), `current` is the latest resumer, and an ordered `chain` array records every operator that ran the session in sequence — so that no intermediate resumer in a three-or-more-operator chain is dropped. The resume invocation MUST still satisfy the real-call / write-enabled flag requirement (per FR-001 and FR-022) — there is no "sticky" or session-inherited promotion of the original invocation's flag. On a resume invocation the original session's `runtime_identity` MUST be PRESERVED and MUST NOT be overwritten — the live runtime does not re-run on resume (there is no new call), so the recorded runtime/model identity remains that of the original connected call (R4-Q12). The recorded runtime/model configuration MUST exclude not only credentials but also provider-account identifiers (e.g., SignalWire project id, real-time-provider account / organization id) — only the provider name and `model_name` / `model_version` are recorded (R4-Q16). Secrets MUST NOT be recorded. On a session that is blocked before any runtime started (a telephony readiness block or a pre-dial gate failure per FR-011, where no Pipecat runtime / live model ever ran), the recorded `runtime_identity` MUST be `null` (absent) on the session and run report — a null `runtime_identity` is the defined and expected value for a pre-runtime block, NOT an omission or error; the run report MUST still record the persona version and run mode for such blocked sessions (per observability CHK029). When a resume invocation cannot recover the original session's operator identity because it should exist but is missing or corrupt (e.g., a corrupt local session record), the run report MUST record `operator_identity.original` as an explicit `unknown` marker (distinct from a legitimately absent value) and surface a warning that the original authorizer could not be recovered, rather than silently dropping the field or overwriting it with the resuming operator's identity (per observability CHK086).

No Slice-3-specific disposition is introduced.
- **FR-018**: The Slice 1 / Slice 2 module boundaries (orchestrator, eligibility evaluator, call transport, persona module, CRM write-back adapter) and their conceptual contracts MUST be preserved. The new Slice 3 SignalWire transport, Pipecat runtime, and shadow STT lane MUST sit behind the existing transport and runtime contracts; the only renames sanctioned at the Slice 1 → Slice 3 boundary are name-only changes catalogued in the Slice 1 SC-008 forward-compatibility review (`mock_provider_call_id` → `provider_call_id`, `MockCallEvent` → `CallEvent`, `fixture_id` → `dial_plan`).

#### Dataverse write-back, idempotency, and resume (preserved from Slice 2)

- **FR-020**: The Slice 2 Dataverse write-back adapter MUST be reused: the same four write-back operations (Phone Call activity emission, queue-status update emission, Task emission, write-back assembly), the same per-disposition emission decisions and per-disposition `new_status` mapping, the same Dataverse metadata two-phase verification (one-time discovery + lightweight live verification before each write-enabled run), the same mapping artifact, the same high-confidence value preservation, and the same owner/team mapping for callback and review Tasks. Slice 3 MUST NOT weaken or delete any Slice 2 Dataverse contract; the only adapter-side addition is recording the real provider call ID on the Phone Call activity payload in place of the mock provider call ID, plus any connected-call timestamps the SignalWire status callbacks supply. The DNC / opt-out field write (FR-024), the blocked-by-eligibility status field write (FR-023), and the dial-blocked status field write (FR-012 provider-rejected dial) are field-level variants of the existing queue-status update emission operation; the write-back operation count remains four for Slice 3.
- **FR-021**: The Slice 2 idempotency-key stamping behavior (a stable session-derived idempotency key stamped onto a metadata-verified Dataverse field of every Phone Call activity and Task, with a pre-query before each create) MUST be reused. Duplicate SignalWire status / media callbacks, repeated CLI invocations for the same session, and write-back retries after a transient Dataverse error MUST NOT create duplicate Phone Call activities, duplicate Tasks, duplicate queue-status transitions, or duplicate attempt-count increments. A duplicate SignalWire callback (same provider event id) MUST be a no-op for state, normalized result, attempt count, and write-back, but MUST still be recorded in the local callbacks audit log.
- **FR-022**: The Slice 2 bounded in-run retry (initial attempt plus up to 3 retries with 1s / 2s / 4s default backoff, optional `Retry-After` honored and capped at 30s), the resume-on-re-invocation behavior (only the missing writes are retried; no duplicate Phone Call activity, Task, queue-status transition, or attempt-count increment is produced), and the local audit retention floor (correlation rows and progress rows retained at least 90 days per the Slice 2 definition) MUST be reused for Slice 3. Every resume re-invocation that performs a Dataverse mutation MUST supply the real-call / write-enabled flag (per FR-001) — there is no "sticky" promotion of the original invocation's flag. A resume re-invocation of a session whose writes ALL already succeeded is a no-op that mutates nothing, so the flag requirement does not block it from succeeding (it cannot mutate either way); such a fully-written-back re-invocation MUST produce no duplicate Phone Call activity, Task, queue-status transition, or attempt-count increment whether or not the flag is supplied, and the run report MUST record the no-op resume outcome. The flag requirement is scoped to invocations that would actually perform a mutation (per deployment CHK089). A resume re-invocation that omits the flag MUST run in rehearsal / readiness mode, which is a no-op for any Dataverse mutation and surfaces in the run report what would have been written. The rehearsal-resume "would-have-written" disclosure is, by intentional design (R4-Q37/Q38), scoped to the run report: the `run_report.json` is the AUTHORITATIVE disclosure surface for what a flag-omitted resume would have written, and stdout is NOT required to carry that disclosure (stdout echoes the run mode per R4-Q36 but is not the disclosure surface). This run-report-only scoping is a ratified, deliberate decision — not a coverage gap — so an operator inspecting `run_report.json` always learns the mutation did not happen, while CI / non-interactive invocations are not stdout-dependent for the disclosure (per ux CHK124). A flag-omitted (rehearsal) resume MUST be NON-DESTRUCTIVE against the local resume state: it MUST NOT consume, advance, or clear any `writeback_progress` ledger entry, MUST NOT emit any new CRM correlation row, write-back row, or audit-row side effect, and MUST leave the missing-writes state exactly as a subsequent flag-supplied real resume would find it — the rehearsal resume reads the local resume state to report what would be written but MUST NOT mutate it, so a later real resume still finds the missing-writes state intact and has nothing spurious to dedup against (per idempotency CHK106 and CHK107).

The **transient-error classifier** governing the retry-vs-abort decision for a Dataverse write is reused verbatim from Slice 2: a Dataverse write error is `transient` (and therefore retried within the FR-022 budget) when it is a connectivity / timeout / throttling / 5xx-class server error or an explicit `Retry-After` response; it is terminal (and therefore NOT retried) when it is a 4xx-class client / validation / authorization error or a metadata-verification mismatch. This CRM-write `transient` predicate is distinct from the `RealtimeProviderError.transient` flag (FR-013), which is a live-runtime concept and does not classify CRM writes (per idempotency CHK044). The FR-022 bounded in-run retry budget applies ONLY to post-dial write-back steps. A transient Dataverse error encountered at the PRE-DIAL Dataverse metadata readiness-verify gate (FR-009 item (f)) does NOT enter the FR-022 retry budget: real-call mode does not tolerate a transient verify failure at the pre-dial gate — the run ABORTS before dial (no dial, no attempt, no Phone Call activity) with the Dataverse-unreachable-at-start exit (exit 7), separate from the readiness-failure exit (exit 4). The retry-vs-abort boundary is therefore location-dependent: pre-dial verify failures abort; post-dial write-back failures retry within budget (per idempotency CHK139).
- **FR-023**: A blocked-by-eligibility queue item MUST result in only the approved Dataverse blocked / status / error field writes — no Phone Call activity, no Task, and no attempt increment — consistent with Slice 1 / Slice 2.
- **FR-024**: A `do_not_call` disposition (or mid-call opt-out) MUST update the Dataverse DNC / opt-out and queue-status fields and MUST NOT create a callback or review Task — consistent with Slice 1 / Slice 2 and the persona policy. On a `do_not_call` outcome the DNC / opt-out field write MUST be attempted FIRST in the write-back sequence — before the queue-status update, before the Phone Call activity emission, and before any Task emission — so that a partial-write-back failure within the FR-022 retry budget that loses everything BUT the DNC write still leaves the contact protected from further automated outreach. Idempotency-key stamping (per FR-021) and the resume contract (per FR-022) prevent duplicate DNC writes when the resume re-invocation runs. If the DNC / opt-out write ITSELF exhausts its FR-022 retry budget (the contact may remain unprotected from further automated outreach), the run MUST halt the remaining write-back, finalize with failure reason `dnc_write_failed`, and emit a PROMINENT operator alert in the run report and on stderr; the resume path MUST retry the DNC write first (R4-Q7).

#### Attempt-count semantics

- **FR-025**: The attempt count MUST be incremented exactly once per session for Slice 3, only after eligibility allows the item, the real-call / write-enabled flag is supplied, real-dial phone-number validation passes, telephony readiness passes, Dataverse metadata verification passes, and the SignalWire dial succeeds (a real provider call ID is assigned). Rehearsal / readiness mode, real-call / write-enabled flag absence, telephony readiness failure, real-dial phone-number validation failure, Dataverse-unreachable-at-start, provider-rejected dial requests, malformed dial-plan / persona-runtime configuration, and duplicate SignalWire callbacks for the same dialed call MUST NOT increment the attempt count.

#### Live-call abandonment and provider-callback handling

- **FR-026**: The orchestrator MUST handle the live-call abandonment case: a call placed and acknowledged by SignalWire that does not receive a normalized terminal event (`no_answer`, `voicemail`, `failed`, `completed`) within the configured live-call abandonment timeout MUST be finalized as `failed` with a `live_call_abandonment` reason; the queue item MUST NOT remain in `in_progress` indefinitely; no false connected-call Phone Call activity MUST be created if the call never reached the connected state; the Slice 2 resume / idempotency behavior applies for any partial write-back. When the operator re-invokes the CLI to resume a session that received the SignalWire `answered` callback but never a normalized terminal event before the orchestrator process died (or callback delivery failed persistently), the resume invocation MUST immediately finalize the session as `failed` with reason `live_call_abandonment` and apply the Slice 2 resume contract for any partial write-back. The resume invocation MUST NOT wait for further SignalWire callbacks for the in-flight call and MUST NOT attempt to reconnect to the provider's media stream — by the time a human re-invokes, the call has been silent past the abandonment timeout.
- **FR-027**: SignalWire status callbacks delivered after a session has been finalized with a disposition MUST be treated as conflicting-late events per the Slice 1 idempotency rules: the finalized disposition MUST NOT change, the normalized result MUST NOT mutate, the attempt count MUST NOT increment, and no new CRM write-back payload MUST be emitted. The conflicting callback MUST still be recorded in the local conflicting-events audit log keyed by `(session_id, provider_event_id)`.

#### Shadow STT (non-blocking) and discrepancy logging

- **FR-028**: When shadow STT is enabled for a Slice 3 run, the shadow lane MUST listen to the same caller audio as the live conversation path and MUST produce an independent transcript or transcript pointer under the same session and retention policy.
- **FR-029**: Shadow STT MUST NOT block live conversation turns and MUST NOT slow the live call path. A shadow-lane failure or timeout MUST NOT abort the live call. The orchestrator MUST NOT delay session finalization to wait for the shadow lane to drain. The orchestrator MAY hold the CRM write-back for a deployment-configurable grace window after session finalization so that a late shadow-STT discrepancy event MAY participate in the disposition per FR-031; if the grace window elapses without a discrepancy event, the write-back MUST proceed without it, and any later shadow-lane output for that session MUST be recorded as a post-finalization audit-only `shadow_lane_truncated` event and MUST NOT mutate the finalized disposition or emit a new CRM write-back payload. The grace-window value in effect for a session MUST be recorded on the session and surfaced in the run report; the default is deployment configuration (no spec-mandated maximum). A grace-window value of `0` is the supported force-immediate-write path — the write-back proceeds without holding for the shadow lane, and any shadow output becomes a `shadow_lane_truncated` event. A shadow-lane FAILURE (the lane crashed, errored, or timed out and produced no usable result) MUST be recorded in the run report as a `shadow_lane_failed` signal that is DISTINCT from `shadow_lane_truncated` (late-but-present output): the two conditions are reported independently so an operator can tell "the lane broke" from "the lane was too slow to participate." When the shadow lane crashes or errors WHILE the grace window is being held open, the crash MUST NOT terminate the held window early: the orchestrator records `shadow_lane_failed` and continues to hold the write-back until the nominal grace window expires (or `grace_window_sec = 0` forces immediate write), then proceeds with write-back — write-back proceeds at the window boundary in all grace-window cases, never earlier on a mid-window crash (per CHK094). When the shadow lane produces a discrepancy event that arrives AFTER the CRM write-back has already completed (e.g., an early Dataverse round-trip finished the write-back before the nominal window boundary), that discrepancy MUST be recorded as a post-finalization audit-only `shadow_lane_truncated` event and MUST NOT mutate the finalized disposition or emit a new CRM write-back payload — once write-back has completed for a session, any later shadow output is audit-only regardless of whether the nominal grace window had elapsed (per CHK097).
- **FR-030**: Shadow STT MUST compare high-value fields (opt-out / DNC, wrong number, captured email, callback intent / preferred callback window, person reached name and role, interest level, and final disposition) against the live conversation path's transcript/log and MUST record discrepancies as audit/review evidence under the session. The shadow lane MUST NOT independently write a CRM record and MUST NOT override the persona's final disposition in the MVP. The full per-high-value-field comparison record — including the AGREEMENT-level outcomes (which fields were compared and agreed), not only the divergences — is surfaced as the run report's structured `shadow_stt.discrepancy_summary` (`{fields_compared, discrepancies, uncertain, per_field:[{field, classification}]}` per FR-036), where `fields_compared` counts all compared fields and `per_field` carries each compared field's classification (including agreeing fields). The standalone per-field divergence records remain a distinct `shadow_discrepancies.jsonl` artifact recording only divergent fields; whether a fuller per-field agreement-level artifact (one row per compared field, agreements included) is materialized to disk separately from the run-report summary is **Deferred to Implementation Plan** — the run-report summary is the authoritative agreement-level comparison surface (per observability CHK057).
- **FR-031**: When the configured shadow STT discrepancy policy classifies a discrepancy as uncertain (rather than a benign formatting / casing difference), the orchestrator MUST escalate the session to `needs_human_review` and MUST create exactly one review Task in Dynamics assigned to the configured review owner with a `shadow_stt_discrepancy` reason code. `shadow_stt_discrepancy` is an additive entry to the Slice 1 `human_review_reason` enumeration; existing Slice 1 reason codes MUST NOT be replaced or repurposed.
- **FR-032**: Shadow STT MUST be deployment-configurable as enabled or disabled. When disabled, the Slice 3 demonstrable loop MUST still complete without it. The run report MUST always state whether shadow STT was enabled for a given run.

#### Transcript retention, redaction, and audit artifacts

- **FR-033**: Transcript and artifact retention for Slice 3 MUST be deployment-configurable, supporting at minimum full-transcript-with-redaction, summary-only, and pointer-only retention modes. Default-on transcript redaction (the Slice 2 default-on `[REDACTED]` policy or its configured replacement) MUST run before any transcript artifact is written to disk. The default-on redaction policy MUST cover the full transcript file, the session-result `summary`, the shadow STT transcript (when shadow STT is enabled), the shadow STT discrepancy records, and the `CallbacksAuditLog.raw_callback_body` field (the stored SignalWire provider callback body, which may echo caller-spoken / PHI-bearing content) — the `raw_callback_body` MUST be passed through the same default-on redaction pass with the same before-write timing as the transcript artifacts (redacted before the audit row is written to disk) (per compliance CHK153); the transcript pointer (and its metadata) is excluded from the default-on redaction policy because pointers MUST remain machine-readable for resume / inspection. The default-on redaction (PHI / value redaction) policy ALSO covers the `actual_writeback.json` and `planned_writeback.json` payload bodies: although these are not transcript-derived, they may carry persona-extracted high-value field values (e.g., a captured email, a callback window, a person-reached name) that fall under the same PHI / value-redaction obligation, so their payload bodies MUST be redacted to the same standard before write — in addition to the SC-018 no-secrets guarantee that already covers them (per observability CHK134). When summary-only retention is configured, no full transcript file MUST be written and the session-result artifact MUST still include the redacted summary, the retention mode, the persona version, and the runtime/model identity.
- **FR-034**: Shadow STT transcript artifacts MUST honor the same retention policy as the live transcript artifact (full + redacted, summary-only, or pointer-only). Shadow STT discrepancy records MUST be retained as audit/review evidence even when transcript retention is summary-only.
- **FR-035**: Logs and exported artifacts MUST NOT contain SignalWire credentials, real-time AI provider credentials, shadow STT provider credentials, Dataverse credentials, or any other secret. The Slice 2 no-secrets-in-artifacts guarantee is preserved. This guarantee EXTENDS to exception messages and stack traces (R4-Q17): the global exception handler MUST pass any error text through the redaction layer before it is logged, surfaced on stderr, or written to the run report. The SignalWire callback signing secret (and every other secret) MUST be loaded from the environment ONLY, at module init; loading a secret from disk or from CLI argv is forbidden (R4-Q20). The no-secrets gate verifying SC-018 MUST be a class-agnostic sweep over ALL artifact classes, not a fixed file-glob (R4-Q21); this explicitly includes `actual_writeback.json` and `planned_writeback.json` as covered artifact classes — the no-secrets guarantee for the real-call `actual_writeback.json` payload is a named-class obligation, not merely an instance of the "any other secret" catch-all (per security CHK168). The global exception handler's redaction pass (R4-Q17) MUST apply BOTH the secret-redaction policy (`[REDACTED]`) AND the PHI tag-and-redact policy (`[PHI-REDACTED]`, per FR-015) to any error text — including exception messages and stack traces — before that text is logged, surfaced on stderr, or written to the run report, so error text cannot leak either a secret or a caller-volunteered PHI span (per compliance CHK151). The signing-secret (and every-secret) load-path restriction — environment-only, at module init, never from disk or argv — is a testable compliance control: a verification check MUST confirm that no secret-bearing configuration key is resolved from a file path, the TOML config surface, or CLI argv (the configuration-precedence rules in §Clarifications restrict secrets to env-var-only with no TOML/CLI surface), so secret provenance is enforceable rather than asserted (per compliance CHK152). The FR-009 SignalWire signing-secret readiness check (`signing secret present and loadable`) MUST confirm only secret PRESENCE / loadability and MUST surface only the check name and pass/fail in the telephony readiness report and its failure message — the secret value MUST NOT appear in the readiness report or any failure message (per security CHK172). The precise enumeration of what constitutes a "secret" beyond the named credential classes (SignalWire, real-time AI provider, shadow STT, Dataverse) and the concrete machine-enforcement surface for the SC-018 class-agnostic sweep are **Deferred to Implementation Plan** — the spec pins the behavior (0 secrets in any artifact class; env-only load; class-agnostic sweep) but the closed secret-enumeration and the static-analysis / scanning mechanism are plan-side, because "or any other secret" is intentionally open-ended to avoid a spec that silently narrows the guarantee (per observability CHK044, security CHK168).
- **FR-036**: The system MUST produce, on every Slice 3 invocation, an operator-readable run report and the local audit artifacts needed to explain — without a custom openCloser UI — the SignalWire provider status, the live conversation outcome, the CRM write-back result, the shadow STT discrepancy status (when shadow STT was enabled), and the failing readiness check or block reason when applicable. At minimum the run report MUST identify the run mode, the session ID, the invoking operator identity, the real provider call ID when assigned, the persona version, the runtime/model identity (recorded as `model_name` + `model_version`, the single canonical shape), the final disposition, the per-write-back-operation status (planned / completed / resume-needed / blocked), the shadow STT enabled/disabled flag and discrepancy summary when enabled, the shadow-lane `lane_truncated` and `lane_failed` signals (reported independently per FR-029), the grace-window value in effect for the session (per FR-029), the telephony readiness summary (each readiness check from FR-009 with its result — labeled `skipped (resume)` on a resume invocation, which never re-dials and therefore does not re-evaluate the pre-dial gates), any callbacks audit / conflicting-callbacks audit row counts, the rejected-by-authentication callbacks count (per FR-008), and any failure or blocked reason (including `redaction_failed` per FR-015, `dnc_write_failed` per FR-024, `live_call_abandonment` per FR-026, and the distinct runtime-failure reason codes `provider_error` / `runtime_crash` / `silence_timeout` per FR-013). On a resume invocation the run report MUST identify the original session's operator identity, the resuming operator's identity (e.g., "resumed by X, original operator Y"), AND the full ordered operator `chain` per FR-016. The operator identity field is local-only (per FR-016) and MUST NOT appear on any Dataverse record.

The run report MUST additionally carry the following observability fields. Bridges connected-call audio between SignalWire and the configured real-time AI model provider, drives the ALF persona's conversation turns, emits transcript segments and extraction events, and returns persona output for the orchestrator to assemble into the Slice 1 normalized session result. Pipecat-specific pipeline shape and the real-time AI provider's streaming protocol live inside this adapter only.
- **Configured Real-time AI Provider**: A deployment-configured real-time audio model provider integrated through Pipecat. Identity is recorded on the session for audit (provider name and model version); credentials are deployment-configured and MUST NOT appear in logs or artifacts.
- **Real Provider Call ID**: The SignalWire-assigned call SID (or carrier-equivalent) for a placed call, recorded on the session and used for correlation with SignalWire status and media callbacks. Replaces the Slice 1 / Slice 2 mock provider call ID for Slice 3 while remaining backwards-compatible for audit inspection of pre-Slice-3 sessions.
- **Telephony Readiness Report**: The local artifact produced by rehearsal / readiness mode (and recorded on every real-call / write-enabled run) listing the result of each telephony readiness check (SignalWire credentials, source number, destination phone format, callback URLs, persona/runtime configuration, Dataverse mapping, callback owner mapping, eligibility). Surfaces the failing check name on any readiness failure.
- **Callbacks Audit Log**: The local audit artifact recording every SignalWire status and media callback received for a session — including duplicates and out-of-order deliveries — keyed by `(session_id, provider_event_id)`. Holds receipt timestamp, callback type, the normalized event the transport produced, and any conflicting-late-event audit row when applicable.
- **Shadow STT Lane / Shadow Transcript**: The optional non-blocking secondary transcript pipeline producing an independent transcript or pointer under the same session and retention policy as the live transcript. Holds the shadow transcript, the per-high-value-field comparison record, and any discrepancy events.
- **Shadow STT Discrepancy Record**: A local audit/review record produced when the live conversation path and the shadow STT lane disagree on one or more configured high-value fields. Holds the session ID, the field(s) that disagreed, the live and shadow values, the discrepancy classification (benign / uncertain), and the resulting review-task reason code when escalation applied.
- **Live-Call Abandonment Outcome**: A finalization path used when a placed SignalWire call does not receive a normalized terminal event within the configured timeout. Produces disposition `failed` with reason `live_call_abandonment`, ensures the queue item leaves `in_progress`, and avoids creating a false connected-call Phone Call activity.
- **Run Report**: The operator-readable Slice 3 run summary covering run mode, session ID, real provider call ID when assigned, persona version, runtime/model identity, final disposition, per-write-back-operation status, shadow STT enabled/disabled and discrepancy summary, telephony readiness summary, callbacks audit row counts, and any failure or blocked reason. The Slice 3 evolution of the Slice 2 run-report artifact.
- **Preserved Slice 1 / Slice 2 Entities**: Queue Item, Eligibility Decision, Session, Mock Call Event (renamed `CallEvent` at the transport boundary for Slice 3), Normalized Result, Phone Call activity payload, Queue-status update payload, Task payload, Idempotency Key, Conflicting Event Audit Record, Conversation Fixture (used only in Slice 1 / Slice 2 fixture-replay debugging in Slice 3), Transport Fixture (same — fixture-replay only in Slice 3), Dataverse Queue Item, CRM Field Mapping Artifact, Dataverse CRM Adapter, Task Owner Mapping, Redaction Layer / Redaction Policy, CRM Correlation Identifier, Write-Back Progress Ledger. These are reused unchanged except for the documented Slice 3 renames (`mock_provider_call_id` → `provider_call_id`, `MockCallEvent` → `CallEvent`, `fixture_id` → `dial_plan` at the SignalWire transport boundary) and the additive `shadow_stt_discrepancy` entry in the human-review reason enumeration.

## Assumptions

- **Slice scope**: Slice 3 explicitly excludes Flutter admin app work, generated Dart clients, mobile/web packaging, tenant-onboarding UI, install-checklist UI, dashboard UI, campaign status UI; multiple telephony providers; app voice/video, avatars, LiveKit, and browser calling; clinical / patient-facing / nurse / doctor / medical workflows; Opportunity creation; custom product UI, campaign UI, analytics dashboard, transcript review console, and replacement CRM task queue; Dograh as a required runtime or campaign system; Celery, Redis-as-a-required-dependency, Kubernetes, broad scheduler / batch processing, multi-worker coordination, distributed job queues, and any generalized workflow engine; raw call-audio capture or storage as a Slice 3 artifact (transcripts — live and shadow STT — are the only Slice 3 audio-derived artifacts; raw-audio capture, its retention modes, its caller-consent surface, and its redaction approach are deferred to a later slice with its own design); and automatic sales qualification beyond the approved ALF appointment-setter disposition, summary, captured email, callback intent, DNC, and review-task fields. These are deferred per the constitution and the openCloser MVP PRD.
- **Bench ownership and contract handoff**: Feature 003 is fully owned by `py-bench`. Any Flutter admin app, generated Dart client, install-checklist UI, dashboard UI, or tenant-onboarding screen work is a later feature in `flutterBench` (Features 004+) that consumes versioned contracts from `py-bench`, fixtures, or generated clients. Feature 003 MUST NOT contain Flutter implementation tasks.
- **Slice 1 / Slice 2 contracts preserved**: The Slice 1 conceptual contracts (queue item, eligibility decision, normalized session result, disposition enum, Phone Call activity payload, queue-status update payload, Task payload, idempotency expectations, module boundaries) and the Slice 2 Dataverse contracts (metadata two-phase verification, mapping artifact, idempotency-key stamping, bounded retry, resume behavior, owner/team mapping, high-confidence value preservation, dry-run/readiness defaults, run report, local audit artifacts, retention floor) are reused unchanged. The only sanctioned amendments at the Slice 1 → Slice 3 boundary are the name-only changes catalogued in the Slice 1 SC-008 forward-compatibility review (`mock_provider_call_id` → `provider_call_id`, `MockCallEvent` → `CallEvent`, `fixture_id` → `dial_plan` at the SignalWire transport boundary) and the additive `shadow_stt_discrepancy` entry in the human-review reason enumeration. No Slice 1 / Slice 2 contract is weakened or deleted.
- **Single campaign, single item**: Slice 3 processes one queue item from one ALF campaign per CLI invocation. Concurrent claims, batch processing, implicit multi-item selection, multi-campaign handling, and multi-worker locking are out of scope.
- **First and only telephony provider**: SignalWire is the only Slice 3 telephony provider. Multi-provider abstraction is out of scope.
- **Voice runtime path**: Pipecat is the only Slice 3 voice runtime. Modular STT → LLM → TTS chains are out of scope as the primary live conversation path; the configured real-time AI model provider is the only Slice 3 primary live conversation model path. Non-blocking shadow STT is the only secondary transcript lane.
- **Persona policy preserved**: The ALF appointment-setter persona policy (AI-on-behalf-of-Medx disclosure, non-clinical scope, no resident/patient PHI collection, opt-out / DNC stop, allowed-claim categories, extraction schema, enumerated human-review reason codes, deterministic disposition precedence) is preserved unchanged. The live model produces conversation turns and extraction events; the deterministic disposition rules and the safety gates remain authoritative.
- **Default safe mode**: The CLI default invocation does not place a SignalWire call and does not mutate Dynamics. An explicit real-call / write-enabled flag (or equivalent deliberate action) is required for live dialing.
- **Hard E.164 validation**: Slice 3 mandates E.164 / provider-acceptable destination phone-number validation before any SignalWire dial. The Slice 2 non-E.164 data-quality warning is promoted to a hard Slice 3 pre-dial block.
- **Live-call abandonment timeout**: A deployment-configured timeout governs the live-call abandonment behavior (FR-026). The configurability is the requirement; the exact default is deployment configuration.
- **Shadow STT toggle and discrepancy policy**: Shadow STT is deployment-configurable as enabled or disabled. The discrepancy policy (which differences are benign vs. uncertain) is deployment-configurable. The configurability and the audit-only / no-CRM-write semantics are the requirements; specific provider choice is deployment configuration.
- **Transcript retention modes**: Full-transcript-with-redaction (default-on redaction), summary-only, and pointer-only retention modes are deployment-configurable. The configurability is the requirement; the deployment owns the policy choice.
- **Backwards-compatible call ID correlation**: The Slice 3 rename of the provider-call-id concept from "mock provider call ID" to "real provider call ID" preserves correlation behavior for replay / audit inspection of pre-Slice-3 sessions. Pre-Slice-3 session artifacts and CRM correlations remain interpretable.
- **Compliance scope**: Slice 3 is a non-clinical ALF business-outreach demo that MUST NOT collect PHI or patient/resident health information. It is explicitly not a HIPAA-class patient-care or clinical workflow. Clinical personas, patient-facing medical workflows, and avatar behavior require a separate PRD, safety model, escalation plan, and constitution review before implementation.
- **Telephony-consent regulatory frameworks (declared out of scope)**: TCPA prior-express-consent / robocall registration, STIR/SHAKEN caller-ID attestation, two-party call-recording consent jurisdictions, and external (federal/state) DNC-registry scrubbing are explicitly OUT OF SCOPE for Slice 3 and deferred to a dedicated compliance-hardening PRD (Round 3 decision). Slice 3 enforces only the local call-window / internal-DNC / attempt eligibility rules (the six Slice 1 rules promoted to hard pre-dial checks) plus the persona's immediate opt-out / DNC stop. These regulatory frameworks are a named exclusion, not an oversight; a production pilot MUST NOT treat Slice 3's pre-dial gates as satisfying them.
- **Local artifact retention**: Local audit artifacts, callbacks audit logs, shadow STT artifacts, CRM correlation / write-back progress rows, the rehearsal-produced `planned_writeback.json`, and the real-call `actual_writeback.json` write-back payload files all follow the Slice 2 retention floor (≥ 90 days, or longer when configured) — the planned/actual write-back payload files are explicitly classified UNDER the ≥ 90-day audit floor (not under the FR-033 transcript retention modes), since they are CRM-write audit evidence rather than transcript-derived artifacts (per observability CHK053, CHK133). Pre-Slice-3 session artifacts retained for backwards-compatible call-ID correlation are likewise placed under the same ≥ 90-day audit floor for as long as they are retained; the Slice 3 floor does not retroactively shorten them, and they remain interpretable per §Backwards-compatible call ID correlation (per observability CHK054). Pruning is a manual operator action; the application MUST NOT auto-delete audit artifacts. The ≥ 90-day floor is a measurable outcome (see SC-022).
- **Operator surface**: The Slice 3 demo path uses CLI / API output, the local run report, local audit artifacts, and the resulting Dynamics records as the operator surface. No custom openCloser UI is part of Slice 3.
- **CRM as control plane**: Dynamics 365 / Dataverse remains the operational source of truth for queue lifecycle, DNC / opt-out, attempt counters, and follow-up tasks in Slice 3. Local state remains limited to session, audit, artifacts, and correlation identifiers, consistent with Slice 2.
- **Slice 2 deployment is a prerequisite (CHK125)**: Slice 3 ALWAYS follows a completed Slice 2 deployment on the same tenant. Therefore the verified Dataverse mapping artifact (`config/dataverse_mapping.json`) produced by Slice 2's one-time metadata discovery already exists before any Slice 3 run, and the Slice 3 quickstart's verify-only step (`opencloser dataverse-verify`) is correct as written — Slice 3 does NOT bootstrap the mapping artifact from scratch, and no one-time mapping-discovery step is part of the Slice 3 cold-start. A brand-new Slice-3-first deployment (without a prior Slice 2) is OUT OF SCOPE for Slice 3; such a deployment must first run the Slice 2 discovery step. This prerequisite is a stated assumption, not an oversight.
- **Forward-only migration (Round 4 R4-Q31)**: Slice 3's schema additions (the additive `sessions` columns and the three new SQLite tables) are backward-compatible — Slice 2 reads ignore them. There is NO automated Slice 3 → Slice 2 downgrade; the documented rollback posture is restoring a pre-migration database snapshot. An already-written-back Dynamics record is never automatically rolled back; recovery is the resume / idempotency path, not a reversal. The forward-only posture extends to the artifact-directory layout: a Slice 2 reader that encounters Slice 3-only files in `artifacts/<session_id>/` (`shadow_transcript.txt`, `shadow_discrepancies.jsonl`, `shadow_lane_truncated.json`, `rejected_auth_callbacks.jsonl`, `conflicting_callbacks_audit.jsonl`, `telephony_readiness.json`, `actual_writeback.json`) MUST tolerate and ignore them — it MUST NOT crash or error on the presence of Slice 3-only artifact files, exactly as Slice 2 DB reads ignore the additive columns and tables. Slice 3-only artifact files are additive and backward-compatible at the directory layer (per deployment CHK134).
- **Retention / redaction policy changes are non-retroactive (CHK142)**: When a deployment changes its retention mode or redaction policy mid-retention-window, the change is NON-RETROACTIVE for artifacts already written to disk: each artifact keeps the `retention_mode` and redaction state it was written under (config-identity stamped per R4-Q46), and a later policy change applies ONLY to artifacts written after the change. Previously-written artifacts are NOT re-redacted or re-classified retroactively; the per-artifact `retention_mode` + `created_at` markers plus the config-identity version/hash make the policy-in-effect-at-write-time auditable for each artifact. The ≥ 90-day audit floor still applies to every audit artifact regardless of a later policy change (per deployment CHK142).
- **Grace-window rollout posture (CHK097)**: A deployment MAY start with a small grace window and tune it upward; coupling the grace-window value to a prerequisite shadow-lane budget measurement before enabling shadow STT is NOT a spec-level requirement. The grace window is deployment-configurable and recorded per session (FR-029), and conservative pilot defaults plus the sanity-ceiling warning (R4-Q32) are the operational guidance; a normative rollout sequence coupling the window to shadow-STT enablement is **Deferred to Implementation Plan** as an operational-tuning decision, not a spec-mandated gate (per deployment CHK097).
- **Audit retention floor is a floor (Round 4 R4-Q33)**: The ≥ 90-day local audit retention floor applies to pointer records and the `artifacts/_unassociated/` tree as well. Deployment configuration MAY set a LONGER retention but MUST NOT lower the audit floor below 90 days for audit artifacts. This is an **auditable invariant**, not merely a behavioral assertion: when deployment configuration sets a retention shorter than 90 days, the 90-day floor still wins for every audit artifact class, the application MUST NOT honor the shorter value for audit artifacts, and the effective-retention precedence (audit floor > configured retention, for audit artifacts) is verifiable via SC-022 (per compliance CHK154). A misconfiguration cannot silently shorten audit retention.
- **Operator-surface scope exclusions (Round 4)**: The following are declared OUT OF SCOPE for Slice 3 and are named exclusions, not oversights: localization / non-English operator output (R4-Q42); a dedicated planned-vs-actual write-back diff UI (operators diff `planned_writeback.json` vs `actual_writeback.json` manually, R4-Q43); a Dynamics-side "who authorized" operator-identity field (operator identity stays local-only per FR-016, R4-Q47); shadow-lane disclosure-text-drift detection (R4-Q45); and callback replay / nonce hardening beyond signature verification + `(session_id, provider_event_id)` dedup (R4-Q22) — the latter deferred to the compliance-hardening PRD.
